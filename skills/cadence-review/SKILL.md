## Task

Audit the change proposal `$mr_ref` (whether a GitLab MR, GitHub PR, or SourceHut patchset) against its governing tier contract -- the approved specification (`spec.md` + `test-plan.md`) at Medium/High tier, or `problem.md`'s Acceptance Criteria checklist at Low tier (resolving `tier` from `metadata.yaml` in Step 2). Run the mandatory Step 0 mechanical pre-scan via `offload_deep_review` and delegate deep adversarial review to the `cadence-reviewer` subagent. Review inputs are completely forge-neutral: `git diff` and `specs/{ticket-id}/submission.md` (the repository's canonical change-proposal record), requiring no forge API connectivity to perform the review itself (`docs/guides/submitting-changes.md`).

## Steps

0. **Mandatory Automatic Mechanical Pre-Scan (`offload_deep_review`).** Once the target branch and integration branch diff (`git diff <integration-branch>...{branch-name}`) are resolved in Steps 1–3, automatically invoke `offload_deep_review` (`local-moe-hybrid` / `gemma-4-26b-a4b` on `:11434`) on the diff **before** delegating to `cadence-reviewer`. The local coprocessor performs an advisory mechanical audit checking:
   - Single-pass readability ceiling (`<400` lines per modified/added file under the Agentic Ergonomics pillar)
   - Comment and docstring preservation discipline
   - Presence of CHORD observability seams (`UNSOUND_CONDITION`, `RULE_DIVERGENCE`, `BOUNDARY_FAULT`, `DELTA_AUDIT_GAP`) and obvious security boundary patterns
   Pass the structured pre-scan report to `cadence-reviewer` in Step 4 so `gemini-4-argon-high` can verify each mechanical flag against the tier contract while focusing primary reasoning capacity on deep adversarial analysis.

1. **Resolve the change-proposal reference:**
   - When `$mr_ref` is an integer, treat it as the forge thread identifier (GitLab MR IID, GitHub PR number, or SourceHut patchset ID). Map it locally to its branch and ticket ID by inspecting `merge_request:` in `specs/{ticket-id}/metadata.yaml` or `Thread URL` under `## Forge metadata` in `specs/{ticket-id}/submission.md`. If local metadata cannot resolve the number, prompt the operator for the branch name (no forge network call is required to resolve the local system of record).
   - When `$mr_ref` is a branch name, use that branch name directly.
   - Parse `{ticket-id}` from the final `/`-delimited segment of the branch name, following the `branch-naming-convention` configured in `CADENCE_ORG.md#branch-strategy-binding` (with full strategy narrative under `docs/policies/branch-strategy/`).

2. **Resolve the ticket's tier and establish the review contract:**
   - Inspect `specs/{ticket-id}/metadata.yaml` and normalize `tier:` (case-insensitively, stripped of surrounding whitespace) **PRIOR to** checking whether `spec.md` exists. The normalized tier determines which artifacts form the review contract.
   - **tier: Low** -> the governing review contract is `problem.md`'s Acceptance Criteria checklist (together with `decisions.md` when present). Never require `spec.md` or `test-plan.md` at Low tier, and never flag their absence as a defect — `docs/policies/change-tiers.md` omits both files at Low tier by design.
   - **tier: Medium or tier: High** -> verify that `specs/{ticket-id}/spec.md` exists and carries approved status. When `spec.md` is absent, flag the missing spec as a process violation while still performing a full code review — **except** when `specs/{ticket-id}/decisions.md` records a mid-implementation tier escalation (`docs/policies/change-tiers.md#escalation`). Before raising a missing-spec violation, inspect `decisions.md` for an escalation entry: if that entry explicitly lists each promoted decision record and explains why each predated and governed the implementation, the absence of `spec.md` is **compliant by escalation ruling** rather than a violation, and those named `decisions.md` entries serve as the review contract. Conversely, an **unqualified** escalation (failing to name the promoted entries or failing to state why each qualifies) is a blocking review finding.
   - **tier absent, empty, or unrecognized** -> NEVER default to Low. Enforce the Medium/High verification rules above and explicitly note in the review report that `tier:` in `metadata.yaml` could not be resolved. Never treat an empty or invalid tier as Low-tier-compliant.

3. **Compute the branch diff** against the repository's integration branch (resolving `<integration-branch>` dynamically from the `integration-branch` marker in `CADENCE_ORG.md#branch-strategy-binding` per `ADR_CADENCE-0020`; never hardcode a branch name):
   ```bash
   git diff <integration-branch>...{branch-name}
   ```
   Execute Step 0's automatic `offload_deep_review` pre-scan on this diff before Step 4.

4. **Delegate to `cadence-reviewer`.** Supply the diff, the tier contract artifacts, and Step 0's `offload_deep_review` mechanical pre-scan so the subagent can:
   - Verify every acceptance criterion against the concrete implementation
   - Audit test coverage and scenario fidelity against `test-plan.md` (or `problem.md` at Low tier)
   - Verify architectural boundaries (Clean Architecture layer direction, service contracts, CHORD seams)
   - Evaluate Engineering Pillars (Structural Simplicity, Operational Resilience, Agentic Ergonomics `<400`-line ceiling, Data & Audit Fidelity, Security Boundary Posture, Surface Compatibility)
   - Verify database migration safety (expand/contract reversibility) where applicable
   - **Core generative principle for the adversarial lens (`AGENTS.md` / `GEMINI.md` §10):** treat every assumption of the form *"this is safe because X"* as an unverified claim that must be checked directly against the authoritative source of X (actual seed-data volumes, vendored engine source/docs, all sibling state writers, production configuration, and canonical story files) — never take the claim at face value; and classify every discovered defect by its structural location relative to the diff: `(1)` inside the diff itself, `(2)` inside upstream code consumed by the diff, `(3)` inside downstream callers consuming the diff, or `(4)` inside untouched sibling code whose invariant the diff silently altered.
   - Apply the **adversarial lens** (`AGENTS.md` / `GEMINI.md` §10): once happy-path spec conformance is confirmed, actively hunt for *silent or partial failure modes* — fallback defaults or stubs that conceal broken state, overly broad exception handlers, unverified assumptions about collaborator behavior (including changes merged to the integration branch after this branch was cut), and test/fake blind spots. Previously approved `decisions.md` entries are not immune to adversarial verification; any silent or partial failure path is a blocking defect. Classify each finding across the four structural positions `(1)`–`(4)` above, scaling depth proportionally to coupling complexity so isolated trivial diffs remain fast. **Never accept a specification's `"out of scope / known limitation / cannot occur at current scale"` disclaimer unverified** — check the actual numbers (seed data counts, default parameter bounds, real payload sizes) and recompute the threshold; any limitation resting on a false numerical premise is an active blocking bug, not future tech debt.
   - Whenever the diff declaratively configures an external engine or framework (map style layers, ORM query builders, CSS layout rules, IaC templates, GraphQL schemas), inspect the **authoritative engine contract** (vendored source or official specification) rather than relying solely on the diff and test doubles — omitted declarative properties interacting with engine defaults are a primary source of production defects.
   - Whenever the diff connects a new field, state atom, or column into a **shared** surface governed by a mutual-exclusivity or consistency invariant (a composite query, serializer/encoder, state reducer, or `"exactly one of"` rule), enumerate **every** writer touching any field in that invariant — including **unchanged sibling writers outside the diff** — and confirm each writer still preserves the invariant. An untouched sibling setter that previously worked in isolation but now leaves the shared invariant violated (e.g., setting one side of a mutually exclusive pair without clearing the newly coupled field) is a blocking defect invisible to narrow diff-only inspection.
   - Whenever a state transition (component mount/hydration, browser back/forward navigation, form reset, or object spread) carries forward a subset of prior state while overwriting other fields, confirm that every retained derived field remains consistent with the overwritten fields (e.g., ensuring a stale map bounding box is not spread forward when center/zoom reset); and confirm that load-bearing integration tests run against the production framework router/container (`createBrowserRouter`, real DI container) rather than a test-only harness that masks the state transition bug.

   **Mandatory re-review after rebasing or merging upstream dependencies.** Whenever the feature branch is rebased onto (or merged with) integration-branch commits that landed after the previous review — such as a collaborator ticket merging upstream — `/cadence-review` must be executed again. A review conducted against an earlier base could not observe interaction bugs introduced when the new upstream collaborator combined with this branch.

5. **Format the review report** as structured change-proposal comments and persist it locally first:
   - Top-level summary containing the overall verdict (`Approve`, `Request Changes`, or `Needs Discussion`) and the per-AC verification checklist
   - File-and-line anchored comments for specific blocking defects and non-blocking observations
   - **Unconditionally** append the complete review record (verdict, AC checklist, and detailed findings) to `specs/{ticket-id}/submission.md` under `## Discussion` so the repository archive preserves the full audit trail regardless of external forge availability.

   Next, publish the review to the external forge **if and only if an MR URL is resolvable**:

   - **MR-existence check.** Look up the MR URL from `merge_request:` in `specs/{ticket-id}/metadata.yaml` **or** `Thread URL` under `## Forge metadata` in `submission.md`. When a URL resolves, posting the review to that forge thread is **MANDATORY**. When **no** MR URL resolves (for example, reviewing a local branch prior to MR creation), the `submission.md` write above is complete — **never** attempt a forge CLI call and **never** treat the absent URL as an error.

   - **Forge publication.** When an MR URL is present, read the `Forge:` type from `submission.md`'s `## Forge metadata`, write the formatted review body to a temporary file, and invoke the matching CLI:
     - **GitHub:** `gh pr comment <pr-number-or-url> --body "$(cat <review-output>)"`
     - **GitLab:** `glab mr note <mr-iid> --message "$(cat <review-output>)"`
     - **SourceHut:** no CLI comment command exists — `submission.md`'s `## Discussion` already holds the canonical record; append a note there instructing the operator to send an email reply to the `lists.sr.ht` patchset thread.

   - **Loud failure reporting.** If `gh` or `glab` exits non-zero, **surface the failure and verbatim CLI error output to the operator**, while confirming that the review was safely persisted in `submission.md`. **Never** swallow a failed forge post silently.

6. **Disposition owed follow-up findings.** Execute this step on **every** review verdict — `Approve`, `Request Changes`, and `Needs Discussion` alike — because non-blocking out-of-scope defects discovered on a rejected proposal still require tracking. **This step is strictly tier-independent**: it branches on neither tier nor status, ensuring an unresolved tier never skips follow-up disposition. At **Low** tier, `/cadence-review` is the final human gate (`docs/policies/change-tiers.md` assigns Low tier no maintainer gate), making this step the primary follow-up filing point. Format each `new` candidate's draft file path as `specs/drafts/{ticket-id}-review-<UTC>-<N>.md` — a single whitespace-free path inside `specs/drafts/` (creating the directory if absent), where `<UTC>` is captured **once per review run** via `date -u +%Y%m%dT%H%M%SZ` and shared across all candidates in this run (DEC-014), and `<N>` is the candidate's 1-based ordinal from sub-step `a`.

   a. **Enumerate and verify finding classes.** Validate every non-blocking finding against `docs/policies/finding-classes.md`: any Non-Blocking entry lacking both an existing disposition in `## Resolution` -> `Follow-ups created` and a valid class token **halts enumeration immediately** (entries already dispositioned in `Follow-ups created` are historical records and exempt from this check). Emit `finding.class.unlabelled` citing the gate (`/cadence-review`), authoring role, and finding text, and prompt the human operator to supply a valid class token; re-prompt at most once on an empty or unrecognized reply, and on a second invalid reply record the entry as `Deferred` citing `finding.class.unlabelled` (never assigning a default class). When the operator supplies a valid class token, record the classification note beside the entry in `submission.md`'s `## Discussion` per `docs/policies/finding-classes.md` Routing step 1 (capturing operator identity and gate `/cadence-review`). If no interactive confirmation channel exists, record the unlabelled entry as `Deferred` citing that cause. Once all entries carry a valid class (or deferral), collect every `out-of-scope-defect` entry from the current review's `#### Non-Blocking` section and `submission.md`'s `## Discussion` that does **not** yet have a recorded disposition in `## Resolution` -> `Follow-ups created` (never re-present an already-dispositioned candidate). Entries classed `nit`, `hygiene`, `observation`, or `adr-owed` are never filing candidates here and remain in `## Discussion` untouched. **When zero candidates remain**, write the none-owed disposition alongside the per-class tally clause (`docs/policies/finding-classes.md`, Routing step 3) and advance to Step 7.

   b. **Verify runtime capability floor.** Filing requires both (i) command-composition support to invoke `/cadence-triage --file-only` and (ii) an interactive channel to obtain human confirmation. **When either capability is missing**, take the degraded deferral path: write each candidate's description verbatim to its `<draft-path>` (`specs/drafts/{ticket-id}-review-<UTC>-<N>.md`) and **leave the draft file on disk** — invoke **no** callee, allocate **no** id, and **never simulate `/cadence-triage`**. Emit the matching diagnostic token — `followup.filing.composition_unavailable` or `followup.filing.confirmation_channel_unavailable` — log each candidate's one-line summary plus its exact `/cadence-triage --file-only <draft-path>` command inside `## Discussion`, and record the deferred disposition naming that token in `Follow-ups created`. Never emit the notice without recording the deferral (or vice versa). When zero candidates exist, nothing is deferred and no notice is emitted. When both capabilities (i) and (ii) are present, never take this degraded branch.

   c. **Prior-work deduplication, presentation, and human confirmation.** Prior to displaying candidates, determine each candidate's prior-work verdict (`docs/policies/finding-classes.md`, Routing step 4) by searching `specs/` and `archive/` (using `local_semantic_embed` / `local-moe-hybrid` plus targeted reads) and tagging each candidate as `new`, `duplicate of <id>`, or `fold into <id>` (citing `<id>`). Never display a candidate without a prior-work verdict. If `specs/` or `archive/` cannot be read, halt and emit `followup.dedupe.check_unavailable` naming the unreadable directory — never default a candidate to `new`. Present the numbered candidate list (one line per candidate with its verdict) and ask the human reviewer which items to file. The agent **proposes**; the human **decides** — never file any candidate without explicit per-candidate confirmation. Note that `cadence-reviewer` (the read-only subagent) only **labels** findings; this top-level skill step executes the disposition.

   d. **Execute confirmed filings and folds.** For each confirmed `new` candidate, first write the candidate's verbatim description to `<draft-path>` (overwriting any prior scratch file at that path), and only after that write succeeds invoke `/cadence-triage --file-only <draft-path>` within the same operation. **Never** invoke `mint-id.sh` or tracker `reserve` directly, and **never** hand-create `specs/<id>/` files — delegating to `--file-only` preserves atomic reserve-and-write pairing. When `--file-only` exits `0`, remove `<draft-path>` (and nothing else); if removing the scratch file fails, emit `followup.filing.draft_cleanup_failed` without invalidating the completed filing. When `--file-only` exits **non-zero**, halt immediately, surface the callee's error **verbatim**, preserve `<draft-path>` on disk as diagnostic evidence, and record any remaining candidates as `Deferred` citing that error. **Never fall back to directory scanning** for a free id. Any candidate already filed prior to a subsequent failure **remains filed and recorded** — never delete an already-filed `specs/<id>/` trail. For each confirmed `duplicate of <id>`, allocate nothing. For each confirmed `fold into <id>`, re-verify at write time that target `<id>` is still open at `draft` or `triaged` (`docs/policies/finding-classes.md`, Routing step 4): if `<id>` has advanced past `triaged`, re-present the candidate as `new` citing `<id>` as related context; otherwise append a dated cross-reference line naming this ticket and `/cadence-review` to `specs/<id>/problem.md` under `## Notes`, record the `folded` disposition once that write lands, and run the bound tracker sync for `<id>` per Routing step 5 (reporting any sync error rather than swallowing it; if the `problem.md` write itself fails, record the candidate as `Deferred` rather than `Folded`).

   e. **Record final dispositions.** Update `submission.md`'s `## Resolution` -> `Follow-ups created` using the six canonical template forms (`filed`, `duplicate`, `folded`, `none owed`, `declined`, `deferred`), appending the per-class tally clause whenever >=1 non-blocking finding was logged. Never leave `Follow-ups created` blank or populated with an unformatted `none` token.

7. **Log code-review stage effort and project to tracker.** In accordance with `docs/agentic-sdlc/CADENCE_ORG.md` "Actual Effort Accumulation", append a `stage_effort` entry to `specs/{ticket-id}/metadata.yaml` (`stage: code-review`, `at` = exact UTC completion timestamp from `date -u +%Y-%m-%dT%H:%M:%SZ`, never rounded, midnight, or date-only) whose `effort` value is computed by running `ci-templates/scripts/stage-effort.sh --stage code-review --observed <minutes>` — resolving the configured stage review multiplier (including any operator override), multiplying, and rounding up to a 15-minute multiple (minimum `15m` for non-zero work; `0m` when the multiplier is `0`). **Verify before saving:** the rounded `effort` string MUST equal `0m` or an exact multiple of 15 minutes; if not, surface a visible diagnostic naming the invalid value, recompute, and continue without halting. Add the increment to `actual_effort`. Across its entire execution, `/cadence-review` performs at most three standard repository writes — Step 5's `submission.md` `## Discussion` mirror, Step 6's `Follow-ups created` update, and Step 7's `metadata.yaml` effort entry — plus up to three conditional writes when triggered in Step 6: (4) appending a fold note to a target ticket's `specs/<id>/problem.md` `## Notes` (followed by syncing `<id>`), (5) recording a Routing step 1 class label note in `submission.md` `## Discussion` when resolving an unlabelled finding in Step 6a, and (6) writing the temporary gitignored scratch file under `specs/drafts/` during Step 6d/6b. The `cadence-reviewer` subagent itself remains strictly read-only, and `/cadence-review` never mutates lifecycle `status`. Finally, invoke the repository's designated tracker sync skill (resolved from `CADENCE_ORG.md` §9, Tracker Binding) for `{ticket-id}` to project the updated `actual_effort` and post the `code-review` worklog.

8. **Report to the operator:**
   - Review verdict (`Approve` / `Request Changes` / `Needs Discussion`)
   - Count of blocking defects
   - Count of non-blocking findings and their follow-up dispositions
   - Concise synthesis of architectural and adversarial review findings

# YouTrack Issue Description Template

This file defines the **structure of the YouTrack issue description** generated by the `claire-sync-youtrack`
skill. The skill does **not** post `problem.md` verbatim -- it fills the template below from repo artifacts
and posts the rendered result as the issue's `description`.

> **Format:** YouTrack **Markdown** (self-hosted YouTrack Server renders issue descriptions as Markdown).
> The sibling adapter restores Jira **wiki** markup here; nothing on this path converts markup in either
> direction, and forcing a wiki restoration would corrupt every projected description (AC-6 divergence 3).
> The body below is already Markdown; only the `{{token}}` values are substituted.

> **Acceptance Criteria live here, in the description (AC-4b, CONFIRMED).** This skill never writes a dedicated
> Acceptance-Criteria custom field, so the `## Acceptance Criteria` section below is the **only** place ACs
> are projected. There is no dedicated AC-field write anywhere in the skill, and therefore no audit line
> for the description-only branch: it is the only branch, so a condition announcing it would fire on every
> run and name none. That retirement is recorded in `youtrack-scripts.md` §8 (AC-6 divergence 2).

## Token sources

Each `{{token}}` is filled from a repo artifact. The repo is the source of truth (sync is one-directional,
repo -> YouTrack). When a source section is absent -- or is present but does not satisfy the Source
requirement stated for that token -- follow the **If missing** rule.

| Token | Source | If missing |
|---|---|---|
| `{{id}}` | `metadata.yaml` `id` | required -- abort if absent |
| `{{title}}` | `metadata.yaml` `title` | required -- abort if absent |
| `{{type}}` | `metadata.yaml` `type` | omit the line |
| `{{priority}}` | `metadata.yaml` `priority` | omit the line |
| `{{tier}}` | `metadata.yaml` `tier` | omit the line |
| `{{status}}` | `metadata.yaml` `status` | omit the line |
| `{{business_context}}` | `problem.md` -> *Business Context* (prose only) | render `_Not yet documented._` |
| `{{problem_description}}` | `problem.md` -> *Problem Description* (prose only) | render `_Not yet documented._` |
| `{{desired_outcome}}` | `problem.md` -> *Desired Outcome* (prose only) | render `_Not yet documented._` |
| `{{acceptance_criteria}}` | `problem.md` -> *Acceptance Criteria* checklist items | drop the whole section |
| `{{functional_validation}}` | `problem.md` -> *Functional Validation* (checklist items, or the explicit no-change line) | render the NOT SPECIFIED marker: _Functional validation NOT SPECIFIED -- this ticket has not stated whether it changes end-user-observable behaviour; do not read this as "no change"._ Never drop the section and never substitute the no-change line. The same rule fires when the section is present but, after HTML comments are stripped, carries neither a non-placeholder checklist item nor the canonical no-change line -- leaving it unfilled is not the no-change state. |
| `{{out_of_scope}}` | `problem.md` -> *Out of Scope* bullets | drop the whole section |
| `{{spec_link}}` | repo path `specs/{{id}}/spec.md` (or `archive/{{id}}/spec.md`) | omit the row |
| `{{merge_request_link}}` | `metadata.yaml` `merge_request` | omit the row |
| `{{spec_mr_link}}` | `metadata.yaml` `spec_mr` | omit the row |
| `{{tags}}` | `metadata.yaml` `tags` (comma-joined) | omit the line |
| `{{elicited_intent}}` | `problem.md` -> *Elicited Intent* (provenance blockquote + one `### <section name>` sub-heading per probed section, each holding `**Source:**`/`**Probe:**`/`**Answer:**` bundles) | drop the whole section |

## Rendering rules

- **Prose only:** strip the `> **Probe:** ...` blockquotes and their `_Answer:_` lines from `problem.md`
  sections -- authoring scaffolding, not issue content.
- **Checklist items:** render `- [ ]` / `- [x]` items from the checklist sections
  (Acceptance Criteria, Functional Validation) as Markdown list items (`- ...`).
- **HTML comments:** strip `<!-- ... -->` comments from `problem.md` sections -- authoring
  scaffolding, not issue content, exactly as the `> **Probe:**` blockquotes are. The
  *Functional Validation* guidance is the first such comment inside a projected section.
- Leave a blank line between a heading and the following paragraph or list.

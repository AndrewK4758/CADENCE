## The link account (BTG-107 AC-1)

Every non-linked outcome for a declared ticket reference increments **exactly one** of three mutually exclusive stdout counters, forming an exhaustive partition of `jira-link.sh`'s non-linked total. Each counter corresponds to a distinct operator remediation:

- **`references_unreadable`** — the declaration in `metadata.yaml` could not be parsed as a valid ticket reference; zero HTTP requests were issued for it. **Remediation:** fix `metadata.yaml`. Initialized from `jira-link-targets.sh`'s refusal count (including any `jq` extraction failure) and never incremented elsewhere.
- **`references_unresolved`** — the reference string was valid, but the target issue could not be verified in Jira due to transport failure, HTTP `401`/`403`/`500`, or a definitive HTTP `404`. **Remediation:** check Jira connectivity/permissions, or sync the referenced ticket first. Both definitive `404` absence and server/auth errors increment this counter (BTG-107 DEC-007), while the specific stderr condition (`referenced_absent` vs. `reference_unresolved`) distinguishes which occurred.
- **`references_skipped`** — the target issue resolved in Jira, but the link itself was not created, completed, or verified during this run (for example, an ordered link skipped because the instance's link types could not be read — see `ordered_skipped` below). **Remediation:** inspect the stderr condition and re-run.

`REJECTED` (which determines whether `link_result` is `rejected`) is computed once as the **exact sum of those three counters** rather than incremented separately, guaranteeing the partition is exhaustive and disjoint by construction. `js_link_emit_account` is the sole function that writes stdout counters, invoked on all seven early-exit paths as well as normal completion.

## Related-ticket links (`jira-link.sh`, best-effort)

- **`syncjs.link.created`** / **`syncjs.link.up_to_date`** / **`syncjs.link.rejected`** — per-pair link outcome. An existing link suppresses creation only when it matches the intended **link type**.
- **`syncjs.link.referenced_absent`** — direct `GET /rest/api/2/issue/<key>` returned a definitive HTTP `404`: the target issue does not exist in Jira, so linking is skipped and counted in `references_unresolved`. **Note (BTG-124 DEC-007):** because BTG-124 removed the `<id>: ` prefix from Jira summaries and retired the summary-search fallback, any `related_tickets` target that is a local repo ID rather than an existing Jira issue key hits `404` and is reported here (degrading cleanly at exit `0` while naming and counting the unlinked reference).
- **`syncjs.link.reference_unresolved`** — the target lookup could not be completed due to transport failure or HTTP `401`/`403`/`500`. Increments `references_unresolved` so `link_result` is `rejected` (never `up-to-date`), and retries on the next sync (DEC-033).
- **`syncjs.link.reference_resolved`** — **RETIRED by BTG-124 (DEC-007) and never emitted.** Previously logged when the retired summary-search fallback mapped a repo ID to a Jira key; documented here so operators searching historical transcripts understand why it no longer fires.
- **`syncjs.link.signal_ambiguous`** — a flat `related_tickets:` item's trailing comment contains keywords for **both** inward and outward link directions simultaneously; falls back to the symmetric default link type rather than guessing a direction and recording dependency order backwards (DEC-032).
- **`syncjs.link.type_undiscoverable`** — `GET /rest/api/2/issueLinkType` failed or returned unparseable JSON; skips ordered link creation rather than guessing a link type.
- **`syncjs.link.type_fallback`** — no link type on the Jira instance matches the configured `precedes` / `is preceded by` phrasing, so the adapter falls back to the symmetric default link type (recording the association while noting that directional ordering was lost). Link types are matched dynamically from `/rest/api/2/issueLinkType` by phrasing rather than trusting hardcoded IDs (DEC-031).
- **`syncjs.link.ordered_skipped`** — an ordered link could not be created because its link type was undiscoverable; never guessed. **BTG-107 AC-1:** increments `references_skipped` so `link_result` reports `rejected` rather than falsely reporting `up-to-date`.
- **Ordered-link direction self-heal** — the sole link deletion `jira-link.sh` ever performs, and the single sanctioned exception to its additive-only invariant. To prevent any failure from leaving two tickets completely unlinked, the properly directed link is **created and verified first** before the reversed link is deleted (DEC-029):
  - **`syncjs.link.direction_reversed`** — an existing link between the two issues has its inward/outward direction inverted; initiates self-heal.
  - **`syncjs.link.direction_healed`** — the properly directed replacement link was created and verified, and the inverted link was deleted.
  - **`syncjs.link.heal_abandoned`** — creating the replacement link was **rejected**, so the existing inverted link is intentionally **left intact** (preserving connectivity until the next run retries).
  - **`syncjs.link.heal_incomplete`** — the properly directed link was created and verified, but `DELETE` on the inverted link failed: **both** links remain on the issue and the stale inverted link requires manual removal.
- **`syncjs.link.related_tickets_value_shape_unrecognized`** — a `related_tickets:` entry (or top-level ordering key entry) cannot be parsed as a valid single ticket key. **Both keyed sub-maps and flat list items emit this single condition name**, with the diagnostic detail identifying the sub-key/position and offending value truncated to 120 characters (BTG-106 DEC-006; BTG-108 DEC-007). Fires on four structural shapes: (1) a sub-key value is a nested map where a scalar or list was expected; (2) a list item is neither a readable string nor a `{ticket: ...}` map; (3) the extracted target string fails the strict ticket-key **ALLOWLIST** (`^[A-Za-z0-9_-]+$` — tightened from a character denylist by BTG-108 DEC-001 to block path traversal or slash-separated strings like `../../etc` or `CTS-61/62` from reaching the REST URL path, PROD_CADENCE-011); or (4) an assembled `<declaring-key> <target>` pair does not consist of exactly two whitespace-separated tokens (catching multi-ticket strings like `"CTS-61 and CTS-62"` or unparsed inline flow maps `{ticket: "CTS-70"}` per BTG-106 DEC-015/DEC-016 and BTG-108 DEC-003/DEC-008). Emitted **prior** to any network call and counted in `references_unreadable`, forcing `link_result=rejected`. Note that a valid list of ticket keys under a sub-key is fully supported and projects one link per element inheriting the sub-key's relation (BTG-106 DEC-001/DEC-002/DEC-004).
- **`syncjs.link.epic_exempt`** — the ticket has `type: epic`; because child membership is represented via the Epic Link field rather than issue links, Step 8 skips cleanly.
- **`syncjs.link.none`** — `metadata.yaml` declares zero related tickets and zero ordering keys; no link calls are made (emitted only when declarations are genuinely empty, never when unreadable).

## Additional link and transition conditions

- **`syncjs.link.link_read_failed`** (Warning) — the target issue's existing `issuelinks` array could not be read, so link creation is **aborted** for that pair. Treating an unreadable link list as "no link exists" would create duplicate links on transient 5xx responses (since Jira Server does not deduplicate REST-created links) and miss inverted links needing self-heal.
- **`syncjs.link.type_fallback`** (Warning) — no link type on the instance matched the configured name (`Duplicate`, `Cloners`, or the ordered link type) case-insensitively, so the symmetric default link type was used (AC-7).
- **`syncjs.transition.hop`** (Info) — the target workflow status is not directly reachable from the issue's current status, so `jira-transition.sh` executes one **governed** intermediate workflow transition and re-queries `GET /transitions` (for example, `Code Review -> In Progress -> Done`). An intermediate hop must be declared in this issue type's `status_workflow_map`, must not have been visited already during this run, and must be **unique** (if two governed intermediate hops are offered simultaneously, the script refuses to guess between paths).

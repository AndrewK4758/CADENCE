### jira-screen-lib.sh

| Field | Value |
|---|---|
| **Operation/step** | Shared library, the SCREEN-AVAILABILITY concern for the projection write — **sourced** by `jira-write-issue.sh` (its sole caller); never invoked as an entry point and runs nothing on load |
| **What it does** | Answers "does the target screen carry this field?" **before** the body is built, so a field the screen will not accept is omitted with a named condition instead of aborting the whole projection with an HTTP 400 (PROD_CADENCE-024, observed live against the reference Jira Server instance). `js_screen_fetch` builds the instance's field map **once per invocation** and memoizes it. The **create** path reads it in **two steps**, reflecting an OBSERVED server behavior rather than a design preference: Jira 9 REMOVED the classic single-shot `createmeta?projectKeys=…&expand=projects.issuetypes.fields`, which answers **HTTP 404 "Issue Does Not Exist"** on Jira Server 9.3.1 because `createmeta` is parsed as an issue KEY. The replacement is keyed on the issue type's **id**, so step 1 is `GET /rest/api/2/issue/createmeta/{project}/issuetypes` to resolve that id by name and step 2 is `GET /rest/api/2/issue/createmeta/{project}/issuetypes/{issueTypeId}`, whose field list arrives as an ARRAY of descriptors at `.values[].fieldId` and is normalized here into the same object map the edit path yields. **Step 2 is issued only when step 1 resolved an id**, so a pre-8.4 instance costs ONE read and resolves UNKNOWN — every field sent as before, reported by name. The **update** path and the follow-up read `GET /rest/api/2/issue/{key}/editmeta`, the endpoint `jira-ac-lib.sh` already uses for this exact question, whose map sits at `.fields`. Four field questions cost ONE map either way, which is what the memo provides (DEC-026). The memo is an **in-process variable**, not a cache layer or filesystem cache: nothing is cached ACROSS invocations (DEC-005 as narrowed by DEC-017). `js_screen_available <field-id>` is **THREE-VALUED** — `0` available, `1` affirmatively absent, `2` unknown — and that is deliberate: a boolean would force callers to collapse "the instance says this field is absent" and "nobody could ask" into one branch, which is the fail-CLOSED mistake DEC-007 forbids. **Only an affirmative absence suppresses**; unreachable, non-2xx, and an unrecognized 2xx body all send the field as normal. `js_screen_guard <field-id> <condition> <var> <suppressed-value> <detail>` is the per-field call site: on an affirmative absence it clears that field's omission sentinel, records the id, saves the pre-suppression value for the follow-up, and emits the named condition; on unknown it ensures the single shared `availability_unknown` has been emitted; on available it does **nothing at all**, avoiding noisy transcript lines when no actionable decision occurred. `js_screen_followup <issue-key>` is the **CREATE-COMPLETION** write: reachable only from the create path, in the same invocation, against the key that invocation just created. It re-queries the **edit** screen (a distinct question from the create screen's), stages ONE body through the shared builder, and issues **exactly ONE** `PUT` carrying every recovered field — never one PUT per field. It **NEVER halts**. The field id reaches the predicate only as a **parameter**: no issue-type name and no field name appears in any control-flow predicate, which makes one implementation govern all four identically and satisfies `sync-jira-server-screen-availability-gate.sh`. It never writes `metadata.yaml` |
| **Inputs** | Its caller's variables, read directly as an in-line block would: `MODE`, `ISSUE_KEY`, `ISSUE_TYPE`, `PROJECT_KEY`, `BASE_URL`, `BODY_FILE`, `DESCRIPTION_FILE`, `ORIGINAL_ESTIMATE`, `PRIORITY`, `LABELS_JSON`. From the instance: the create-screen or edit-screen field map. Nothing from the config sidecar — this concern introduces **no config key, no toggle, and no environment variable** (DEC-004: where a field is available, behavior is byte-identical, leaving nothing for an adopter to opt out of) |
| **Outputs (stdout)** | **None of its own.** It sets `JS_SCREEN_SUPPRESSED` and `JS_SCREEN_RECOVERED` for its caller, which resolves them into `estimate_result` — the enum gains **`field-unsupported`** (the estimate was suppressed and not recovered) and **`followup-written`** (the create-completion write landed it), both additive. Its audit lines go to **stderr** only, under the `syncjs.estimate.*`, `syncjs.priority.*`, `syncjs.labels.*`, `syncjs.description.*`, and `syncjs.screen.*` prefixes, all catalogued in `.agents/skills/cadence-sync-jira/jira-server-conditions-screens.md`. **The fetched field map is never printed, never logged, and never written to a file**: it describes the instance's screen configuration for an issue type, only per-field booleans are derived from it, and it lives in a shell variable that dies with the process (Pillar 7, Source Confidentiality) |
| **Exit codes** | Returns `0` from every function on every path, and **HALTs its caller's process on nothing at all**. That is the contract: a guard that could halt the projection would duplicate the defect it exists to remove, so an unresolved probe, a rejected follow-up, and an unstageable follow-up body are each **reported and returned from**. The verdict is a return status and a variable, never an exit code, preventing a caller from collapsing "the field was withheld" into "the step failed". It installs **no `trap … EXIT`** (BTG-079 AC-3): the shell keeps only one EXIT trap per process, so a trap armed inside a sourced library function would REPLACE its caller's — which is also why the follow-up reuses the caller's already-trapped body file rather than staging a second temp file with its own lifecycle |
| **Re-run (idempotency)** | Naturally idempotent in two senses. The **probe** is a read: the same screen configuration always yields the same per-field verdicts without mutating the instance. The **follow-up** writes only fields that the create suppressed, so a re-sync of the same ticket takes the update path against the edit screen, suppresses nothing that the edit screen supports, and issues no follow-up at all — the second write exists only on the create that needed it. If an administrator changes a screen configuration between runs, the verdict legitimately updates and reports the change rather than hiding it |

# `/claire-sync-jira` — script contracts: screen availability

Bounded context: Tracker projection / Jira Server-DC adapter (BTG-075, BTG-168).
Invariant relied on from outside this boundary: identical to its sibling
`.claude/skills/claire-sync-jira/jira-server-scripts.md` — the repository (`metadata.yaml` +
`problem.md`) is the source of truth; Jira is the projection layer, and every script communicates on
exactly three channels (stdout `key=value`, stderr `syncjs.*`, exit code).

**This file is a fifth part of one index, not a fifth index.** It was split off by BTG-168, which
relocated the whole screen-availability concern out of `jira-write-issue.sh` — a file whose 395-line
ceiling the predicate plus the follow-up write would have carried past 400 outright, and whose FIRST
body-staging call and FIRST update write `btg-102-retype-guard.test.sh` SS-1 locates **positionally**, so
a second inline update write would land a new site inside an assertion that reasons about ordering. The
record is **split, never truncated** — the same facet-conflict resolution BTG-105 applied to the umbrella
entries, BTG-102 to the condition catalogue and BTG-173 to the issue-type entry (C-3: Operability
outranks DX on *content*; DX is served by the placement instead). The seam is the question "does this
write ask the instance before sending a field?". `btg-075-script-contract.test.sh`'s `js_index_view`
merges every `jira-server-scripts-*.md` into the primary before each lookup, so a split cannot hide a
missing contract entry.

Its reported conditions are catalogued in

### jira-screen-lib.sh

| Field | Value |
|---|---|
| **Operation/step** | Shared library, the SCREEN-AVAILABILITY concern for the projection write — **sourced** by `jira-write-issue.sh` (its sole caller); never invoked as an entry point and runs nothing on load |
| **What it does** | Answers "does the target screen carry this field?" **before** the body is built, so a field the screen will not accept is omitted with a named condition instead of killing the whole projection with an HTTP 400 (PROD_CLAIRE-024, observed live against the reference Jira Server instance). `js_screen_fetch` builds the instance's field map **once per invocation** and memoizes it. The **create** path reads it in **two steps**, and that is an OBSERVED fact rather than a design preference: Jira 9 REMOVED the classic single-shot `createmeta?projectKeys=…&expand=projects.issuetypes.fields`, which answers **HTTP 404 "Issue Does Not Exist"** on Jira Server 9.3.1 because `createmeta` is parsed as an issue KEY. The replacement is keyed on the issue type's **id**, so step 1 is `GET /rest/api/2/issue/createmeta/{project}/issuetypes` to resolve that id by name and step 2 is `GET /rest/api/2/issue/createmeta/{project}/issuetypes/{issueTypeId}`, whose field list arrives as an ARRAY of descriptors at `.values[].fieldId` and is normalized here into the same object map the edit path yields. **Step 2 is issued only when step 1 resolved an id**, so a pre-8.4 instance costs ONE read and resolves UNKNOWN — every field sent exactly as today, reported by name. The **update** path and the follow-up read `GET /rest/api/2/issue/{key}/editmeta`, the endpoint `jira-ac-lib.sh` already uses for exactly this question, whose map is at `.fields`. Four field questions cost ONE map either way, which is what the memo buys (DEC-026). The memo is an **in-process variable**, not a cache layer and not a filesystem cache: there is still nothing cached ACROSS invocations (DEC-005 as narrowed by DEC-017). `js_screen_available <field-id>` is **THREE-VALUED** — `0` available, `1` affirmatively absent, `2` unknown — and that is deliberate: a boolean would force callers to collapse "the instance says this field is absent" and "nobody could ask" into one branch, which is the fail-CLOSED mistake DEC-007 forbids. **Only an affirmative absence suppresses**; unreachable, non-2xx and an unrecognized 2xx body all send the field exactly as today. `js_screen_guard <field-id> <condition> <var> <suppressed-value> <detail>` is the per-field call site: on an affirmative absence it clears that field's own omission sentinel, records the id, saves the pre-suppression value for the follow-up, and emits the named condition; on unknown it ensures the single shared `availability_unknown` has been emitted; on available it does **nothing at all**, because a line on the available branch would appear in every adopter's transcript on every sync for no decision anyone can act on. `js_screen_followup <issue-key>` is the **CREATE-COMPLETION** write: reachable only from the create path, in the same invocation, against the key that invocation just created. It re-asks the **edit** screen (a different question from the create screen's), stages ONE body through the shared builder, and issues **exactly ONE** `PUT` carrying every recovered field — never one PUT per field. It **NEVER halts**. The field id reaches the predicate only as a **parameter**: no issue-type name and no field name appears in any control-flow predicate, which is what makes one implementation govern all four identically and what `sync-jira-server-screen-availability-gate.sh` asserts structurally. It never writes `metadata.yaml` |
| **Inputs** | Its caller's variables, exactly as an in-line block would read them: `MODE`, `ISSUE_KEY`, `ISSUE_TYPE`, `PROJECT_KEY`, `BASE_URL`, `BODY_FILE`, `DESCRIPTION_FILE`, `ORIGINAL_ESTIMATE`, `PRIORITY`, `LABELS_JSON`. From the instance: the create-screen or edit-screen field map. Nothing from the config sidecar — this concern introduces **no config key, no toggle and no environment variable** (DEC-004: where a field is available the behaviour is byte-identical, so there is nothing for an adopter to opt out of) |
| **Outputs (stdout)** | **None of its own.** It sets `JS_SCREEN_SUPPRESSED` and `JS_SCREEN_RECOVERED` for its caller, which resolves them into `estimate_result` — the enum gains **`field-unsupported`** (the estimate was suppressed and not recovered) and **`followup-written`** (the create-completion write landed it), and both are additive. Its audit lines go to **stderr** only, under the `syncjs.estimate.*`, `syncjs.priority.*`, `syncjs.labels.*`, `syncjs.description.*` and `syncjs.screen.*` prefixes, all catalogued in `.claude/skills/claire-sync-jira/jira-server-conditions-screens.md`. **The fetched field map is never printed, never logged and never written to a file**: it describes the instance's whole screen configuration for an issue type, only per-field booleans are derived from it, and it lives in a shell variable that dies with the process (Facet 7, Source Confidentiality) |
| **Exit codes** | Returns `0` from every function on every path, and **HALTs its caller's process on nothing at all**. That is the contract, not an accident: a guard that can halt the projection is a second copy of the defect it exists to remove, so an unresolved probe, a rejected follow-up and an unstageable follow-up body are each **reported and returned from**. The verdict is a return status and a variable, never an exit code, so a caller cannot collapse "the field was withheld" into "the step failed". It installs **no `trap … EXIT`** (BTG-079 AC-3): the shell keeps exactly one EXIT trap per process, so a trap armed inside a sourced library function would REPLACE its caller's — which is also why the follow-up reuses the caller's already-trapped body file rather than staging a second temp file with its own lifecycle |
| **Re-run (idempotency)** | Naturally idempotent, and in two senses. The **probe** is a read: the same screen configuration always yields the same per-field verdicts, and nothing about it mutates the instance. The **follow-up** writes only fields the create suppressed, so a re-sync of the same ticket finds those fields already present on the issue's screen, suppresses nothing, and issues no follow-up at all — the second write exists only on the create that needed it. A screen configuration an administrator changes between runs legitimately changes the verdict, and the change is reported rather than absorbed |

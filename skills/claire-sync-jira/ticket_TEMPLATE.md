# Jira Server/DC Ticket Description Template

This file defines the **structure of the Jira issue description** generated by the
`claire-sync-jira` skill. The skill does **not** post `problem.md` verbatim — it fills the
template below from repo artifacts and posts the rendered result as the issue's `description`.

> **Format:** Jira **Server/DC wiki markup** (the v2 REST API renders descriptions from wiki
> markup, not ADF/JSON). The body is already wiki markup; only the `{{token}}` values are
> substituted. Do **not** wrap the rendered result in code fences when sending it to Jira.

## Token sources

Each `{{token}}` is filled from a repo artifact. The repo is the source of truth (sync is
one-directional, repo → Jira). When a source section is absent -- or is present but does not
satisfy the Source requirement stated for that token -- follow the **If missing** rule.

| Token | Source | If missing |
|---|---|---|
| `{{id}}` | `metadata.yaml` `id` | required — abort if absent |
| `{{title}}` | `metadata.yaml` `title` | required — abort if absent |
| `{{type}}` | `metadata.yaml` `type` | omit the line |
| `{{priority}}` | `metadata.yaml` `priority` | omit the line |
| `{{tier}}` | `metadata.yaml` `tier` | omit the line |
| `{{status}}` | `metadata.yaml` `status` | omit the line |
| `{{business_context}}` | `problem.md` → *Business Context* (prose only) | render `_Not yet documented._` |
| `{{problem_description}}` | `problem.md` → *Problem Description* (prose only) | render `_Not yet documented._` |
| `{{desired_outcome}}` | `problem.md` → *Desired Outcome* (prose only) | render `_Not yet documented._` |
| `{{acceptance_criteria}}` | `problem.md` → *Acceptance Criteria* checklist items | drop the whole `h2.` section |
| `{{functional_validation}}` | `problem.md` → *Functional Validation* (checklist items, or the explicit no-change line) | render the NOT SPECIFIED marker: _Functional validation NOT SPECIFIED -- this ticket has not stated whether it changes end-user-observable behaviour; do not read this as "no change"._ Never drop the section and never substitute the no-change line. The same rule fires when the section is present but, after HTML comments are stripped, carries neither a non-placeholder checklist item nor the canonical no-change line -- leaving it unfilled is not the no-change state. |
| `{{out_of_scope}}` | `problem.md` → *Out of Scope* bullets | drop the whole `h2.` section |
| `{{spec_link}}` | repo path `specs/{{id}}/spec.md` (or `archive/{{id}}/spec.md`) | omit the row |
| `{{merge_request_link}}` | `metadata.yaml` `merge_request` | omit the row |
| `{{spec_mr_link}}` | `metadata.yaml` `spec_mr` | omit the row |
| `{{tags}}` | `metadata.yaml` `tags` (comma-joined) | omit the line |
| `{{elicited_intent}}` | `problem.md` → *Elicited Intent* (the section `/claire-elicit` appends: a provenance blockquote, then one `### <section name>` sub-heading per probed section, each holding `**Source:**`/`**Probe:**`/`**Answer:**` bundles) | drop the whole `h2.` section |

## Rendering rules

- **These rules ship an implementation — use it, do not re-derive it.** The mechanical
  Markdown-to-wiki half of every rule below is performed by `jira-md2wiki.sh`, a pure
  deterministic filter co-located in this directory (contract:
  `jira-server-scripts-render.md`). Pipe each Markdown fragment through it rather than
  converting by hand: hand conversion is what produced the seven recurring defects
  BTG-205 catalogued, each independently rediscovered by adopters. The rules below stay
  the human-readable statement of the mapping, and remain authoritative for the half the
  filter does not perform — deciding *what* a description says, which stays
  model-performed (BTG-205 DEC-001, superseding BTG-150 on the markup axis only).
- **Prose only:** strip the `> **Probe:** …` blockquotes and their `_Answer:_` lines from
  `problem.md` sections — they are authoring scaffolding, not ticket content.
- **Markdown → wiki markup:** `**bold**` → `*bold*`, `` `code` `` → `{{…}}` (monospace),
  `- item` → `* item`, fenced blocks → `{code}…{code}`, `#`/`##` → `h1.`/`h2.`.
- **Checklist items:** render `- [ ]` / `- [x]` items from the checklist sections
  (Acceptance Criteria, Functional Validation) as plain `* ` bullets (Jira wiki markup
  has no checkbox syntax in descriptions).
- **HTML comments:** strip `<!-- ... -->` comments from `problem.md` sections — they are
  authoring scaffolding, not ticket content, exactly as the `> **Probe:**` blockquotes are.
  The *Functional Validation* guidance is the first such comment inside a projected section.
- **Escaping:** wiki markup is whitespace/character sensitive — leave a blank line between a
  heading and the following paragraph or list.
- **Elicited Intent sub-structure:** render each `### <section name>` sub-heading as
  `h3. <section name>`; the `**Source:**`/`**Probe:**`/`**Answer:**` labels convert under the
  general bold rule; the section's leading provenance blockquote is retained as a
  `{quote}…{quote}` block. Answer text is **content-preserving** — never paraphrased,
  summarised, truncated or re-ordered — and is still converted to wiki markup under the
  *Markdown → wiki markup* rule above, which takes precedence over any literal reading of
  "verbatim"; internal blank lines are preserved. The *Prose only* strip rule does **not**
  apply inside this section: it targets the `_Answer:_` italic placeholder lines under the
  five per-section probes, which are a different, disjoint set of lines from these
  `**Answer:**` bold-label bundles.

The repository is the source of truth ({{id}}). Edits made in Jira will be lost.
{panel}

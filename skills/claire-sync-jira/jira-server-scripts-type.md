# `/claire-sync-jira` — script contracts: the issue-type decision

Bounded context: Tracker projection / Jira Server-DC adapter (BTG-075, BTG-102, BTG-173).
Invariant relied on from outside this boundary: identical to its sibling
`.claude/skills/claire-sync-jira/jira-server-scripts.md` — the repository (`metadata.yaml` +
`problem.md`) is the source of truth; Jira is the projection layer, and every script communicates on
exactly three channels (stdout `key=value`, stderr `syncjs.*`, exit code).

**This file is a third part of one index, not a third index.** It was split off by BTG-173, which
relocated the whole issue-type concern out of `jira-write-issue.sh` — a file standing at 399 lines
against an assertion that fails at `>= 400`, so the untyped-update path could not add one line to it.
The record is **split, never truncated** — the same facet-conflict resolution BTG-105 applied to the
umbrella entries and BTG-102 applied to the condition catalogue (C-3: Operability outranks DX on
*content*; DX is served by the placement instead). The seam is the question "is the issue type
written, and to what?". `btg-075-script-contract.test.sh`'s `js_index_view` merges every
`jira-server-scripts-*.md` into the primary before each lookup, so a split cannot hide a missing
contract entry.

Its reported conditions are catalogued in
`.claude/skills/claire-sync-jira/jira-server-conditions.md` (the re-type guard's three verdicts) and
`.claude/skills/claire-sync-jira/jira-server-conditions-type.md` (the two untyped-ticket conditions).

### jira-type-lib.sh

| Field | Value |
|---|---|
| **Operation/step** | Shared library, the ISSUE-TYPE decision for the projection write — **sourced** by `jira-write-issue.sh` (its sole caller); never invoked as an entry point and runs nothing on load |
| **What it does** | Owns the two halves of one question. `js_type_resolve` maps the repo's `type:` onto this instance's issue type through `js_config_map issue_type_map`, and **HALTs `4`** when a type the repo *did* assert cannot be resolved — a guessed issue type is an ungoverned decision. It carves out exactly ONE sanctioned exception, added by BTG-173: an **UNTYPED** ticket on the **UPDATE** path sets `TYPE_UNASSERTED=yes`, reports `syncjs.write.type_unasserted`, and leaves `ISSUE_TYPE` empty, so the write **declines to restate a type the repo does not hold** rather than halting. `/claire-triage --file-only` files without classifying (`/claire-triage` F3 writes `tier: ""` and no `type:`) and F5 then mandates the projection, so before BTG-173 the sanctioned filing path halted at step 4 of 9 on every Jira-Server-bound adopter (reproduced 4/4 downstream). Declining to assert is **not** guessing: the issue already carries the type `.claude/skills/claire-sync-jira/jira-reserve.sh` gave it, and the update simply omits `issuetype`. The exception is narrowed twice, and both narrowings are load-bearing — it keys on **emptiness**, never on lookup failure, so a NON-EMPTY unmapped type still HALTs and a genuine config gap can never be swallowed; and it keys on **update**, so `--mode create` with an empty type still HALTs, because a create must carry a type and there is no live value to leave alone. Whitespace-only counts as empty, using the same `[^[:space:]]` normalization the caller's title guard applies, because two writers of one concept must not disagree. `js_type_verdict` is BTG-102's pre-flight **re-type guard**, relocated here byte-for-byte: on the update path it reads the LIVE issue type (reusing the estimate prerequisite's body when it has one, at no extra round trip) and, when the live type diverges from the target, asks `GET .../editmeta` whether the instance offers the target **before** the type is written — because Jira Server/DC's update `PUT` does **not** enforce the types its own `editmeta` offers (OBSERVED, `archive/BTG-102/decisions.md` DEC-026: PLAYSCRUM-3395 accepted a re-type to a type its `allowedValues` excluded, with HTTP 204, stranding it on a status its new workflow does not contain and collapsing its transitions 6 → 2). Every unusable answer resolves to *indeterminate*, never to *allowed* and never to *refused*; unknown fails **closed** on the issue type alone, and every other field still projects. BTG-173 **BYPASSES** the guard when the type is unasserted, and that is behaviour rather than tidiness: left running against an empty target it would compare `Task` against `""`, ask `editmeta` about `""`, receive `refused`, and instruct the operator to perform a Jira **Move to a type that does not exist** — a false instruction on the happy path. It never writes `metadata.yaml` (AC-6) |
| **Inputs** | Its caller's variables, exactly as the in-line blocks read them: `TICKET`, `TICKET_TYPE`, `MODE`, `ISSUE_KEY`, `BASE_URL`, `LIVE_ISSUE_JSON`. From the config sidecar: `issue_type_map`. From the instance: `GET /rest/api/2/issue/{key}?fields=issuetype` (only when the caller has no live body already) and `GET /rest/api/2/issue/{key}/editmeta` (only on a divergence) |
| **Outputs (stdout)** | **None of its own.** It sets `ISSUE_TYPE`, `TYPE_UNASSERTED` and `ISSUETYPE_PROJECTED` for its caller, which gates the `issuetype` member on `ISSUETYPE_PROJECTED` and is the sole emitter of `issuetype_projected=yes\|no`. Its audit lines go to **stderr** only, under the `syncjs.write.*`, `syncjs.config.*` and `syncjs.transport.*` prefixes, and are catalogued in `.claude/skills/claire-sync-jira/jira-server-conditions.md` and `.claude/skills/claire-sync-jira/jira-server-conditions-type.md` |
| **Exit codes** | Returns `0`, never a verdict-bearing status — the verdict is a variable, not an exit code, so a caller cannot collapse "the type was withheld" into "the step failed". It **HALTs** its caller's process on two conditions only: `4` (`JS_EXIT_CONFIG`) when a type the repo asserted cannot be resolved, and `3` (`JS_EXIT_TRANSPORT`) when the instance could not be **asked** — "the exchange could not happen" is never conflated with "the exchange happened and the answer is unusable", because the first must send no write at all. It installs **no `trap ... EXIT`** (BTG-079 AC-3): the shell keeps exactly one EXIT trap per process, so a trap armed inside a sourced library function would REPLACE its caller's |
| **Re-run (idempotency)** | Pure decision, no state of its own: the same repo type, the same live type and the same edit metadata always yield the same verdict, so a re-run re-asserts nothing. A **type that already equals the target asks nothing and costs nothing** — no `editmeta` call is issued — and an **unasserted** type asks nothing either, so the untyped path is strictly *cheaper* in round trips than the typed one. Re-running against an issue a human re-typed in Jira meanwhile cannot fight the change: with nothing asserted there is nothing to write back, and with something asserted the instance is asked first |
